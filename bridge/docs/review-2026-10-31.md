## 二、P0：还没修，建议尽快处理

### 1. `cli/arena-responses` 是 0 字节空文件

README 组件表、`docs/arena-bridge.md`、`codex/config.toml.example`、`cli/arena-codex` 四处都指向它，但仓库里这个文件是空的。也就是说**Codex TUI 这条链路在当前仓库里跑不起来**，而且失败方式很难懂（tmux 起一个空 node 进程，然后 Codex 报连接错误）。

两条路，选一条：

- **要么补上**。核心是把 Responses 映射到 chat/completions，需要实现的事件大致是：`response.created` → `response.output_item.added` → 若干 `response.output_text.delta` → `response.output_item.done` → `response.completed`，入参 `input`/`instructions`/`previous_response_id` 转成 `messages`。约 150 行，零依赖。
- **要么删掉**。从 README 组件表移除 `arena-codex` / `arena-responses` 两行，把 Codex 当"待做"写进路线图。**留着空文件比没有更糟**——它会让人以为功能存在。

### 2. 没有任何鉴权

服务只绑 `127.0.0.1`，这点是对的。但实际用法是 `ssh -L 17892` 把端口转发到手机上，于是**手机上的任意进程**都能：

- 用你的 Arena 账号发问（消耗额度、可能触发风控）
- `GET /debug` 拿到当前标签页 URL（含会话 id）
- `POST /upload` 把本机文件外发（第 6 项已加白名单，但默认仍不限制）

低成本的补法：`ARB_TOKEN` 环境变量，非空时校验 `Authorization: Bearer`，`/health` 放行：

```js
const AUTH = process.env.ARB_TOKEN || '';
function authorized(req) {
  if (!AUTH) return true;
  const h = String(req.headers.authorization || '');
  return h === 'Bearer ' + AUTH;
}
// createServer 开头：if (!authorized(req) && u.pathname !== '/health') return send(401, ...)
```

客户端侧 aichat 的 `api_key` 本来就要填，现在填 `sk-arena-local` 是摆设，正好可以真用起来。

### 3. `arb.ps1` 用命令行参数传 prompt，长问题必挂

`arena-send` 把 base64 塞进 `powershell -File ... -PromptB64 <很长>`。Windows 命令行上限（经 cmd 时 8191 字符）会先撞上，base64 被截断后 PowerShell 解出乱码——表现为一个莫名其妙的失败。中文大约 1700 字就够撞到。

本轮加了**发送前预检并明确报错**，但这只是止血。真正的修法是让 prompt 走 stdin 或临时文件：

```powershell
# arb.ps1 改为
$p = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($PromptB64))
# → 改成从标准输入读整段 base64，命令行只留 session/mode
```

配合 `arena-send` 侧 `printf '%s' "$PB64" | pc "powershell -File arb.ps1 -Session ..."`。

### 4. 任何错误都 `resetSession`，代价被算错了

`/v1/chat/completions` 和 `/ask` 的 catch 里无条件杀会话。可"no stream appeared"这种瞬时问题，重开后要重新加载页面（约 10 秒），而且会把这个会话累积的历史一起丢掉。建议区分：`NEED_VERIFY` / `fatal` → 杀；超时类 → 保留标签页重试一次。

## 三、P1：可靠性

- **没有取消**。客户端断开后任务继续跑（最长 10 分钟），占着全局队列。`res.on('close')` 时标记 aborted，`askOnce` 里每轮 poll 检查一次就够。
- **输入慢且校验弱**。逐字符 `dispatchKeyEvent`，6000 字 = 6000 次 CDP 往返，光敲字 6~20 秒。而且只在结束时校验"非空"，不校验**长度对不对**——中间丢字符不会发现。建议：`await c.ev(VAL_JS)` 与 `body.length` 比对（忽略空白），不等就补敲差量。
- **队列语义被文档误读**。`MAX_QUEUE=4` 是**队列长度**，并发恒为 1。文档写"并发 上限 4"，容易让人以为能并行。
- **`s.busy` 是死字段**，只赋值不读。
- **`histories` 键空间无上限**。按客户端传的 `user` 字段无限增长（每条封顶 24 条消息，但键数量不限）。
- **`res.write` 忽略背压**。长流 + 慢客户端时内存会涨；量不大，但 SSE 写失败目前是静默吞掉的。
- **Chrome 拉起只认 `schtasks`**。`ensureChrome` 里写死 Windows 计划任务，换 Linux/macOS 就是"等 60 秒然后失败"。

## 四、P2：架构与可维护性

### 1. 887 行单文件，零测试

最大的技术债不是长度，是**没有可以单独测试的边界**：流解析逻辑 `parseLine` 埋在 `askOnce` 里，要测它就得连 Chrome。

最划算的一步重构（半天，风险低）：把帧解析抽成纯函数放进 `lib/parse.js`：

```js
// parseFrame(f) -> { text?, reasoning?, tool?, routed?, done?, error? }
```

它要处理的输入种类是明确且有文档的：`a0:` / `ag:` / `a2:` / `a3:` / `ad:` / `data: {records:[{body}]}`。这些都可以用手写样本覆盖，`node:test` 就够，不需要任何依赖：

```js
test('a0 帧是正文', () => assert.equal(parseFrame({l:'a0:"你好"'}).text, '你好'));
test('a3 帧是上游错误', () => assert.throws(() => parseFrame({l:'a3:"boom"'})));
test('records 里的 text-delta 累积', () => ...);
```

这一步做完，以后 Arena 改帧格式时，是"改一个函数 + 跑测试"，而不是"再连一次真机猜"。

### 2. OpenAI 兼容性缺口

| 缺口                                                  | 影响                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------- |
| `tools` / `tool_choice` 被忽略，从不返回 `tool_calls` | 任何真正靠函数调用的客户端（Codex 之外的 agent 框架）都用不了 |
| `usage` 填的是**字符数**，不是 token                  | 客户端算费用/上下文占用全错                                   |
| 无 CORS 头                                            | 浏览器里的调试面板/网页客户端连不上                           |
| 不支持 `n` / `stop` / `max_tokens`                    | 静默忽略，行为与声明不符                                      |

`tools` 这块其实只差最后一公里：页面里的 `tool-input-available` 帧已经把 `toolName` 和 `input` 抓到了（现在只当成 `reasoning_content` 里的装饰文字打印）。把它映射成 OpenAI 的 `tool_calls` delta 即可。
